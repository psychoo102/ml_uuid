# Publishing releases

A push of a new tag matching `v*` runs the existing three-platform build.
One publication job waits for **all** matrix jobs to succeed. Branch pushes
and pull requests build and test but do not publish releases.

## Release contents

| Asset | Target / installation |
| --- | --- |
| ml_uuid-win32.dll | Windows x86; install as ml_uuid.dll |
| ml_uuid-win64.dll | Windows x64; install as ml_uuid.dll |
| ml_uuid-linux-x64.so | Linux x64; install as ml_uuid.so |
| ml_uuid-notices.zip | Project and third-party notices; retain with distribution |
| SHA256SUMS | SHA-256 hashes of the four assets above |

Build output is staged before artifact upload, preserving unique platform
names. Missing, empty, or ambiguous build output fails the job.
The publication job downloads each expected artifact explicitly and validates
the three binaries and required notices before calling the release action.

Publication uses GitHub's built-in `GITHUB_TOKEN` with `contents: write` only
on the release job. A custom `TOKEN` repository secret is no longer needed.
Repository/organization policies must allow that write permission.

Release notes are generated by GitHub. Tags containing a hyphen (for example
`v1.1.3-rc.1`) are marked as prereleases; ordinary version tags are releases.
Concurrent workflow runs for the same ref are serialized.

## Maintainer steps

1. Resolve the remaining SDK provenance and platform verification items in
   [release review](release-review.md).
2. Update project/package versions and merge the desired source and workflow changes.
3. Choose an unused version tag on that commit. For example, after updating to 1.1.3:

   ```sh
   git switch main
   git pull --ff-only
   git tag -a v1.1.3 -m "Release v1.1.3"
   git push origin v1.1.3
   ```

4. Check the Actions run and confirm all five assets are present in the release.
   Checksums can be verified on Linux with `sha256sum -c SHA256SUMS`.

The workflow must be present in the tagged commit. Rerunning a historical tag's
old workflow does not pick up this fix. Prefer a new version rather than moving
an existing public tag. This change does not modify existing release assets.

The publication job waits for builds, but success is not proof that a module
loads in MTA. The MTA integration test remains a separate verification step.
Packaging the notices also does not resolve the SDK licensing question.

## Failure recovery

A failed platform job prevents publication. Missing downloads/inputs fail
before the release API call. A network/API failure during upload can still
leave a partially uploaded release; inspect it and rerun the failed publication
job. Existing same-named assets are replaced by the release action on a rerun.

## Validation

Packaging regressions can be run without a compiler or MTA:

```sh
python -m unittest discover -s scripts -p "test_prepare_release.py" -v
```

The tests cover platform names, checksums, preserved notices, absent/empty
binaries, missing licenses, and ambiguous build output. CI runs them on all
three build targets.
